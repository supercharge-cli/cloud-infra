# Pause & resume

We follow the official E2B docs:

- [Auto-resume on request](https://e2b.dev/docs/sandbox/auto-resume)
- [Auto-pause](https://e2b.dev/docs/sandbox/persistence#auto-pause)

## Create (required)

Default E2B behavior is **`onTimeout: 'kill'`**. Without lifecycle config, sandboxes **die** after the timeout instead of pausing.

```js
const sandbox = await Sandbox.create({
  template: 'xibecode-full-sandbox',
  timeoutMs: 15 * 60 * 1000,
  lifecycle: {
    onTimeout: 'pause',   // not kill
    autoResume: true,     // wake on SDK / public HTTP activity
  },
})
```

Gateway env (already set):

```bash
XIBECODE_E2B_ON_TIMEOUT=pause
XIBECODE_E2B_AUTO_RESUME=true
XIBECODE_E2B_SANDBOX_TIMEOUT_MS=900000
```

## What wakes a paused sandbox

| Activity | Auto-resumes? |
| --- | --- |
| `sandbox.commands.run(...)` | Yes |
| `files.read` / `files.write` | Yes |
| HTTP to sandbox public host | Yes |
| Dashboard **Wake** / any gateway exec | Yes (SDK) |
| Telegram long-poll **inside** paused VM | **No** (process frozen) |
| Telegram → **host webhook** → gateway SDK | **Yes** |

## Telegram DMs

Per E2B: when a message arrives, trigger any SDK operation — no manual `connect()` required if `autoResume: true`.

Vectra does this by:

1. Registering a **host** Telegram webhook (`PUBLIC_BASE_URL/api/telegram/wake/:id/:secret`)
2. On DM → gateway `wake` → `commands.run` / connect → sandbox resumes
3. Restart daemon + re-set webhook (daemon deletes webhooks for long-poll while running)

### Required for production Telegram wake

```bash
PUBLIC_BASE_URL=https://your-public-https-host
```

Telegram cannot call `http://127.0.0.1`. Use a tunnel (ngrok, Cloudflare) or real deploy URL, then **Save & restart** config with the bot token again so `setWebhook` runs.

## New sandboxes only

Lifecycle is fixed at **create**. Destroy old instances and create new ones after this fix so they get `pause` + `autoResume`.
